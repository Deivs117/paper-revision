--- Caveat (why this number cannot go into results.tex as-is) ---
Self-check passed (all 5 test vectors match the Python reference within
1e-3) -- the forward-pass logic itself is confirmed correct on real
hardware, corroborating the earlier host-gcc cross-check.

However, mean latency = 49.892 ms/inference is ~30,000x slower than the
host PyTorch number (1.64 us) and ~1000x slower than what an ESP32-S3 would
be expected to show. Root cause: the ESP32-C3 (RISC-V, this board) has NO
hardware FPU -- every `float` multiply/add in the ~32,600-FLOP forward pass
is emulated in software. The ESP32-S3 (Xtensa LX7, dual-core, the chip the
physical robot's firmware actually targets -- see
PETER_SIMULATION/Repository/Peter_arduino/platformio.ini) has a hardware
single-precision FPU, so its real latency should be dramatically lower and
is NOT extrapolable from this number by a simple clock-speed ratio (it's an
architecture difference, not just a frequency one).

Author decision (2026-08-29): keep this result on file for traceability,
do NOT write anything into results.tex yet. Re-run identically
(`pio run -e esp32-s3-devkitc-1 -t upload`, same firmware/, no code
changes needed -- the S3 env in platformio.ini was already there from the
original plan) once a real ESP32-S3 is available, and append that result to
this file before touching the paper.

--- This IS the number for the paper ---
Self-check passed exactly (5/5 vectors match the Python reference within
1e-3) on the actual target hardware (ESP32-S3, matching
Peter_arduino/platformio.ini). Mean per-inference latency: 8.814 ms
(SD 2.672 us, N=1000). This is ~5,000x slower than the host PyTorch number
(1.64 us) despite the S3 having a hardware FPU -- plausible given: (a) the
firmware does a naive scalar (non-vectorized) triple nested-loop matmul,
no SIMD/DSP instructions used; (b) all weight arrays (~47K float32,
~188KB) are `static const`, i.e. resident in flash and read through the
flash cache rather than RAM, which is far slower per-access than a
host CPU's L1/L2 cache; (c) -O2 only, no explicit loop unrolling/vectorization
flags. None of this invalidates the number -- it is what this exact
firmware, as specified in the plan, actually measures on the real target
chip -- but it explains why it's not host-comparable, and is worth noting
alongside the number in results.tex.
RAM footprint: 24,140 B (7.4% of 320KB). Flash footprint: 397,829 B
(30.4% of the board's 4MB partition, of which the MLP weights header
account for ~397KB of the ~398KB delta over an empty sketch -- i.e. almost
all of it is the model itself, matching Section 3.1's ~47K-parameter count).
